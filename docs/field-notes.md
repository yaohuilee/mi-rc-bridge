# 踩坑记录与实测证据

记录范围从 Windows 识别遥控器开始，到不依赖 WSL 的 Windows 桥接实测录音为止。实验对象是一只 `2717:32B0`，接收端为一台 Windows 11 主机的 Intel `8087:0026`。

## 1. 配对成功，Windows 只识别部分键

Windows 先后将遥控器显示为 `MI RC` 和「小米语音遥控器」。小房子一类按键在输入框可能弹出上下文菜单，部分方向键也可以收到。Raw Input 看不到的其他键，需要往下看 HCI 或 ATT。

USBPcap 在蓝牙 USB 控制器上看到了 `0x0030` 的按下、松开报告，其中有确认、方向和音量等键。说明这些键的信号已到主机。通过早期按键工具做 Windows 键注入，可补齐映射。该工具接入一条已经存在的连接时，用设备信息或电量特征发起公开 GATT 读取，对照 ATT 句柄及时间区间定位同一个 HCI 连接。已连接遥控器无需为了启动抓包而拆电池或重配对。如果 Windows 已经映射同一键，桥接可能产生重复。

## 2. 原生 HID 和 Windows GATT 写入失败

原先捕获只看到按键，体感报告没有自动开始。重启 HID 接口也没有触发重新读描述符，重新配对的 ATT 抓包才取得完整 Report Map。描述符有键盘和六轴，GATT 枚举则另外显示私有 Feature 报告。

| 尝试 | 实测记录 |
|---|---|
| 打开 Windows 键盘 HID 集合读写 | 返回 Win32 错误 5。查询或只写打开时，HID caps 的 Feature 长度是 0 |
| `HidD_SetFeature` | 对该集合写报告 `0x04` 返回 Win32 错误 1 |
| Windows GATT 写 `0x003B` | GATT 可枚举到候选和 `0x2908`，写入返回 `0x80070001`，抓包没有对应 ATT 写请求 |

管理员重试依然遇到同样的 Feature 写入失败。Windows 键盘集合由系统独占，且缺少私有报告的标准 HID 映射。被动 USBPcap 可观察流量，启用仍需要能发送 ATT 的后端。 [微软 HID 客户端架构](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/hid-architecture)

## 3. 从小米盒子固件确定体感控制

用小米盒子 MDZ-16-AA 对应的系统包核对型号。包元数据为 `Xiaomi/JurassicPark/JurassicPark:5.1.1/LMY47V/386:userdebug/release-keys`。将 OTA 的 `system.new.dat` 按块区间重建为只读 ext4 镜像，提取蓝牙相关模块、`sensord` 以及遥控器键位文件。分析 ARM 指令和 Java DEX 调用时，沿传感器启用、报告写入和设备匹配找到 Feature 前缀。用本机 ATT 抓包验证实际发送值、写响应与随后出现的六轴通知。仓库提供已验证的命令和 Report Map，固件系统镜像、第三方二进制和厂商 OTA 都由读者从有权使用的来源取得。

一次打开两组传感器时，曾只见一组三轴变化。分别打开加速度计和陀螺仪并留出间隔，两种先后顺序都能得到同一帧六轴数据。当前实现采用先加速度计，再等约 4 秒打开陀螺仪。

## 4. WSL + Bumble 配对和连接

把控制器通过 usbipd-win 交给 WSL2 后，Bumble 能独立发送 ATT 写请求。Legacy BLE、无输入输出、保留 bond 的配置完成了配对。把配对密钥保存为后端本地状态，可重连并恢复加密。程序先尝试直连，超时后扫描同一地址。首次配对无广播时，短暂断电再重按组合键是恢复手段，正常重连依靠唤醒。

第一次排查容易混淆 Windows 已配对、WSL BlueZ 配对和 Bumble 保存的 LTK。三个状态由不同软件维护。启动器只交接同一块控制器，并明确停止 WSL 内的 BlueZ 服务以免同时访问 HCI。Bumble 的 LTK 不通过监视窗口或 UDP 共享。

## 5. 空鼠和按键转换

陀螺仪的零偏会在静止时累积成漂移。空鼠在静放时采一组稳定样本，用中位数估计零偏。低通滤波抑制瞬时噪声，死区消除小幅静止抖动，关闭空鼠或重新校准时释放可能按住的鼠标键。

本机打开空鼠时，独立的 Windows 测试窗口收到返回键的右键按下和松开。↑ 产生 `+120`，向上滚动；↓ 产生 `-120`，向下滚动；长按能重复。空鼠关闭时的事件门控用模拟输入验证，曾开启本机第二轮等待实体按键，但没有采到那轮的三键报告，因此没有把它列为真机关闭态通过。

## 6. 麦克风和语音截断

Windows 蓝牙配对后没有生成麦克风。检查同一盒子系统的 `Bluetooth` DEX、JNI 和 `audio.primary.amlogic.so`，找到 `BleRemoteControllerService` 对 `32B0` 的语音控制，以及 Dialog ADPCM 分支。每次语音开始由主机向报告 `04` 写启动，遥控器用三个 Feature 通道轮转传音频。用 WSL 探针得到 2,314 个 20 字节包，解出 92,560 个样本，包速率对应约 16 kHz。验证了高半字节在先和持续的解码状态。

语音有时只录到开头。基线抓包发现，按住约 9.8 秒时，桥接在收到 `00 03 …` 诊断报告约 0.4 秒后提前发送停止。修复后，只有类型 `00` 的控制报告会改变按键状态。真松键时才发送停止。另一个干扰项是语音期间看见零运动帧时监视窗口会清空空鼠校准，造成语音结束后还得静放。现已保留同一连接内的校准，让收到新报告时继续使用。

## 7. 语音期间体感停发

修好提前松键后，直接从 HCI 同时统计语音和六轴消息。一次约 9.9 秒语音中收到 3,923 个音频包，六轴只在开头出现一帧。录音中重新发送传感器启用命令、调整 BLE 连接参数（含 7.5 ms、零 peripheral latency）都未恢复六轴。两项实验改动已撤回。松键后约 15 ms 收到第一帧，之后恢复约 50 Hz。

暂停发生在主机 HCI 可观察点之前。当前结果支持遥控器一侧在录音时停止六轴上报，内部调度或资源使用尚未确定。本项目未实现边说话边用体感移动指针。恢复逻辑用实测六轴回放验证，真实松键到屏幕指针移动的端到端延迟未测得。

## 8. Windows 本机版和虚拟麦克风

Windows 与 WSL 两个后端共用 BLE 和语音协议。最终的本机版用 Windows Python 连接 usbipd-win 的本机端口并直接提交 USB/IP 请求，省掉 WSL 实例。已有 bond 在同一物理控制器上迁移后可重用。公开版首次启动可独立配对。

| 验证点 | 结果 |
|---|---|
| Windows USB/IP 回环连接 | `python.exe` 连接 `127.0.0.1:3240` |
| WSL 状态 | 没有正在运行的发行版 |
| 六轴数据 | 原配对加密重连，命令行记录 1,929 帧 |
| 应用侧录音 | 独立 Windows 录音进程从 `CABLE Output` 录到 9.1 秒 WAV，含前后静音，16 kHz / 单声道 / PCM16 |
| 松键后 | 录音尾部 0.5 秒的 PCM 绝对峰值为 1 |
| 正常停止 | 遥控器确认停止采样，适配器恢复 `Not shared` |

VB-CABLE 的端口方向容易选反。桥接写 `CABLE Input`，录音应用读 `CABLE Output`。安装驱动曾改变 Windows 默认播放设备，把默认扬声器改回原设备后，桥接仍可显式写虚拟线缆。
